## 这一阶段要达到什么

让多个进程轮流运行，保存并恢复各自的执行位置。进程暂时无法继续时可以睡眠，条件满足后再被唤醒；退出后，状态和资源应当按规则回收。

先用简单轮转策略把机制做正确。优先级、多级队列等策略属于可选扩展，不代替基本的切换、睡眠、唤醒和退出验证。

进程状态可以先用“可运行、运行中、睡眠、退出待回收”等名字表达。具体状态集合和父子进程操作以详细课件为准。

## 建议的模块布局

以下是候选职责布局，不是现有功能清单。

| 候选文件 | 负责什么 |
|---|---|
| `proc/process.c` | 分配进程记录、维护状态与资源归属 |
| `proc/scheduler.c` | 选择可运行进程，协调每核调度循环 |
| `proc/lifecycle.c` | 退出、等待与最终回收，按需加入创建或复制 |
| `proc/sleep.c` | 在条件或通道上睡眠，配对唤醒 |
| `trap/context.S` | 保存和恢复内核函数切换所需的上下文 |
| `trap/user_trap.c` | 用户陷入与时钟事件中判断是否需要让出 CPU |
| `syscall/process.c` | 接入让出、退出、等待等用户服务 |
| `include/process.h` | 声明状态、上下文和进程接口 |
| `user/sched_demo.c` | 生成能区分各进程的输出或计算结果 |
| `tests/scheduler.c` | 检查切换、并发所有权与资源回收 |

中断保存的是被打断程序的完整现场；内核函数间的上下文切换通常保存 ABI 要求保留的寄存器、栈和返回位置。两种现场用途不同，不宜混成同一块结构。

## 哪些前阶段接口需要扩展

每个核心需要“当前运行进程”的状态，而不再假定全系统只有一个用户进程。同一个进程不能同时被两个核心选中。

Lab 3 的时钟处理需要向调度层提供让出 CPU 的时机。实际切换应发生在允许切换的位置，不能持有任意驱动锁就跳到其他进程。

进程 VM 切换需要切换对应页表与内核栈；返回用户时恢复正确的进程现场。资源回收不能释放仍在运行的栈或仍被使用的页表。

睡眠接口需要与保护条件的锁配合，避免“检查条件后、真正睡眠前”丢失唤醒。后续磁盘等待会依赖这一点。

退出、等待和创建失败需要明确负责回收的人。若课件要求 `fork` 等调用，再在该机制上接入，而非提前承诺完整 Unix API。

## 建议的实现顺序

1. 明确进程状态、每核当前进程及锁的归属。
2. 实现上下文切换，用两个内核执行上下文验证栈与寄存器。
3. 让两个用户进程主动让出 CPU，验证完整用户往返。
4. 接入时钟驱动的调度，确认计算型进程都获得执行机会。
5. 实现睡眠与唤醒，再完成退出、等待和清理。
6. 从单核检查扩展到多核，确认状态竞争与资源计数正确。

每一步都保留上一阶段的用户权限检查，不能为了切换方便而共享所有用户内存。

## 实现后怎样观察和验收

| 观察项目 | 应该看到的结果 |
|---|---|
| 多进程进展 | 多个进程完成独立计算，不出现某个进程一直得不到 CPU |
| 上下文 | 栈、保留寄存器和用户结果经过多次切换仍正确 |
| 多核所有权 | 同一 PID 在任意时刻只由一个核心执行 |
| 睡眠唤醒 | 条件满足后被唤醒；重复高频事件不丢失唤醒 |
| 退出等待 | 返回预期状态，退出资源最终被回收 |
| 故障隔离 | 一个用户进程异常终止，其他进程仍可运行 |
| 内存计数 | 多轮创建、运行、退出后资源返回基线 |

可以提供有限长度的调度事件环，记录“时间、核心、PID、原因”，由诊断命令读取。不要在每次时钟中断中大量打印，免得改变被观察的调度行为。
