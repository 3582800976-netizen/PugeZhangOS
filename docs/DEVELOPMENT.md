# 怎样沿现有框架继续开发

当前运行基础是 `lab3/`，已完成中断和内存管理。Lab 4–9 的目录目前保存规划说明，尚未参与构建。

## 文档和生成文件放在哪里

- 根 `docs/` 只放全系统路线、开发约定和课程依据。
- 单个实验的说明写在它的 README；个人记录随实验放在 `labN/docs/NOTES.md`，有实际内容再创建。
- 验证日志放在 `labN/docs/evidence/cpuN/`，本实验汇总放在同一 `evidence/summary.txt`。Lab 0 的环境构建和运行记录直接放在自己的 `docs/evidence/`。
- 编译产物放在本实验 `build/`，由 Git 忽略。全实验检查的总结果只打印到终端，不生成根目录合并日志。
- 过期设计和重复日志移出当前项目，旧版本通过 Git 历史或项目外备份查阅。

## 阶段如何接续

1. 开始 Lab 4 时，把 Lab 3 的源码模块、头文件、链接脚本和 Makefile 作为基础放入 `lab4/`，保留 Lab 4 自己的说明。
2. 在 `proc/`、`user/` 加入新功能，并通过 `mm/`、`trap/` 的公开接口接入；前阶段的现有能力要继续工作。现有 VM 公开接口只有初始化、启用和查询；用户页表的创建、映射、回收与安全复制接口需要在新阶段增加。
3. 更新 Lab 4 的构建与检查入口，增加验证用户执行的实际测试。当前 `scripts/check.py` 只支持已实现的 Lab 1–3。
4. 通过本阶段检查之后，再以完整 Lab 4 版本发展 Lab 5。以前的目录保留当时版本，便于回看和比较。
5. 写明真实提交、Agent 帮助和本人实际操作。不会为了目录或分支名补造过去的实验历史。

现在不提前复制 Lab 3 的代码到 Lab 4 并改一个启动数字：那样会让阶段名称和实际能力不一致。

## 模块边界

| 内容 | 应放在哪里 | 对外怎么使用 |
| --- | --- | --- |
| 启动顺序 | `kernel/main.c` | 安排调用，不包含命令解析和完整测试 |
| 每核启动状态 | `kernel/bootstate.c` | 查询快照、发布完成；内部数组不外露 |
| 页分配、页表 | `mm/` | 现有物理页申请/释放和内核映射查询；新阶段补充用户映射及复制接口 |
| 保存现场、事件分发 | `trap/` | 调用驱动或进程处理，不运行 Shell |
| 设备寄存器、DMA、完成通知 | `drivers/` | 给上层提供读写和完成接口 |
| 进程状态和调度 | `proc/` | 创建、运行、等待、退出和选择下一进程 |
| 用户到内核的入口 | `syscall/` | 检查参数，通过用户内存复制接口访问数据 |
| 磁盘数据块复用 | `block/` | 上层取得并释放块缓存 |
| inode、路径和文件对象 | `fs/` | 向系统调用层提供文件语义 |
| 诊断展示 | `monitor/` | 读状态接口，展示实际结果 |
| 检查编排 | `tests/` | 使用真实路径，比较不变量和边界 |

函数声明放 `include/`。模块私有状态尽量使用 `static`，其他模块通过接口访问。只有接口变化需要调用者调整，不把一个模块的所有内部结构都公开。

## 在多核内核中怎样拥有资源

- 一个物理页同一时刻由明确的调用者拥有，释放时检查状态。
- 进程内核栈、用户页和页表在进程结构中记录归属，生命周期结束后按归属回收。
- 修改共享页表涉及其他核心正在使用的翻译缓存；现有初始化完成后不再改共享映射的做法不能直接当作动态用户内存方案。
- 中断处理函数缩短工作量；需要等待 I/O 时，由进程等待机制处理。
- 锁保护的状态和锁的使用顺序随模块一同说明。不要在持有只能忙等的锁时执行需要睡眠的等待。

这些是设计原则。新增操作需要结合当次课件和实际代码明确实现，不能仅靠文档当作已经解决。

## 怎样检查和理解

完成一个新模块后，先验证它对外承诺的行为，再运行受影响的前阶段能力。实验目录中的构建产物、日志和 README 必须与该阶段能力一致。

本人可以从三件事参与：理解并决定接口、亲手观察实际输出、解释一个关键执行路径。Agent 可以协助实现、整理文档和运行验证。当前不把额外的小练习当作推进门槛，也不会代填本人理解记录。
