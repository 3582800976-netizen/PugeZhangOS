## 这一阶段要达到什么

磁盘按编号存取数据块；内核先发出请求，设备稍后完成。驱动应当能够把一个块读到内存，也能够把内存中的一个块写回磁盘。

缓冲缓存把最近使用的数据块留在内存，减少重复读取。它还负责同一磁盘块的共享和同步，让不同进程不会各自拿一份内容却互相覆盖。

本阶段先验证块设备与缓存，不把原始数据块叫作文件。目录、路径和 inode 在 Lab 8 中接入。

## 建议的模块布局

以下是候选文件职责，设备细节需根据实际 QEMU 配置核对。

| 候选文件 | 负责什么 |
|---|---|
| `drivers/virtio_blk.c` | 初始化 virtio 块设备、提交请求、处理完成通知 |
| `include/virtio_blk.h` | 描述驱动向上提供的块请求接口 |
| `block/buffer.c` | 按设备和块编号查找、引用和释放缓冲块 |
| `include/buffer.h` | 声明缓冲对象、有效状态与访问规则 |
| `trap/trap.c` | 将块设备完成中断交给驱动，再完成 PLIC 应答 |
| `proc/sleep.c` | 请求等待与完成唤醒；沿用 Lab 6 机制 |
| `monitor/diagnostics.c` | 展示请求数、缓存命中与错误统计 |
| `tests/block.c` | 验证读写、并发请求与缓存一致性 |
| `tools/mkfs.py` | 后续镜像准备工具；此阶段先生成明确大小的测试镜像 |

`tools/` 中的程序在宿主 Linux 运行，不属于内核。Lab 8 确定文件系统布局后，再完善镜像中的元数据生成。

## 哪些前阶段接口需要扩展

构建和 QEMU 启动入口需要明确指定实验磁盘镜像。验收使用专门测试镜像，不覆盖其他实验或个人数据。

VM 需要映射实际块设备寄存器；驱动需核对设备版本与能力。描述符队列使用设备可访问的物理内存，提交请求前后处理必要的内存顺序。

PLIC 分发目前用于 UART，需增加块设备来源。设备处理和 PLIC 完成应答各有明确责任，不能遗漏完成或把设备请求的完成当成同一概念。

驱动等待要调用 Lab 6 的睡眠机制。中断处理只标记完成并唤醒，不在其中做复杂缓存替换或等待另一个请求。

缓存需要区分“条目索引的锁”与“具体块内容的使用权”。明确引用计数、有效状态、写回时机和释放规则，避免持有自旋锁进行可能睡眠的操作。

## 建议的实现顺序

1. 准备带固定测试内容的独立镜像，确认 QEMU 设备配置。
2. 初始化 virtio 队列，完成单次已知块读取。
3. 写入测试块并读回，检查内容和错误处理。
4. 接入完成中断与睡眠唤醒，处理多个请求。
5. 在驱动上构建缓存，定义引用和写回规则。
6. 验证缓存命中、并发同块访问和请求资源回收。

缓存替换策略先保持简单；准确性和锁的边界比复杂策略更重要。

## 实现后怎样观察和验收

| 观察项目 | 应该看到的结果 |
|---|---|
| 已知块读取 | 内容与镜像预置字节完全一致 |
| 写入读回 | 写入指定测试块，重新读取后内容一致 |
| 设备完成 | 请求提交、完成中断和等待者唤醒能够对应 |
| 重复读取 | 缓存命中增长，设备实际读取次数减少 |
| 并发同块 | 内容一致，引用正确，不产生两个冲突缓存条目 |
| 边界错误 | 越界块号和设备错误返回失败，内核仍可继续 |
| 资源回收 | 请求描述符与缓冲引用没有持续泄漏 |

可以展示一条“读块路线”：缓存查询 → 命中或设备请求 → 等待 → 中断完成 → 返回。这条路线显示真实计数和状态，帮助解释设备为何异步完成。
