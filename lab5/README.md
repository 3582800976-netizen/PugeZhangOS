## 这一阶段要达到什么

系统调用是用户程序请求内核服务的入口。用户程序把请求编号和参数放进规定的寄存器，执行 `ecall`；内核检查请求，完成服务，再把结果交还给用户程序。

先提供少量足够演示的调用，例如查询进程编号、输出字符串和申请用户内存。完整文件接口由 Lab 9 接入；这里不假装已有磁盘文件。

用户指针是“不可信的地址参数”。内核必须检查对应用户页是否存在、权限是否合适、长度是否越界，不能直接把传入地址当普通 C 字符串读取。

以下文件仅代表候选职责，实际名字和编号需结合课件确定。

| 候选文件 | 负责什么 |
|---|---|
| `syscall/dispatch.c` | 根据系统调用编号分发，处理未知编号 |

| `syscall/console.c` | 从用户内存复制数据后输出到控制台 |

| `user/usys.S` | 把用户 C 函数调用转换成 `ecall` |
| `user/lib.c` | 用户侧字符串、简单输出等辅助函数 |
| `tests/syscall.c` | 检查合法调用、错误参数与内存边界 |

保留原有模块分工；系统调用层调用进程和内存层，不把所有服务堆到 `trap/user_trap.c` 里。

## 哪些前阶段接口需要扩展

用户陷入处理需要识别 U 模式 `ecall`，把保存现场中的参数交给系统调用层。正常完成时推进这条已知的 `ecall` 指令，而非对所有异常一律增加 PC。

用户 VM 需要支持指定进程的地址空间。建立页时区分读、写、执行权限；回收时归还页表和数据页，刷新必要的地址翻译缓存。

需要统一的用户内存复制入口。检查地址加长度的整数溢出、跨页范围、未映射页和只读目标；避免“检查第一字节后直接复制整段”的漏洞。

进程记录需保存用户内存大小或区域范围。内存增长失败应保持原状态，并释放本次新申请的资源。

串口驱动继续只负责设备；它不负责验证用户指针。验证和复制发生在内核系统调用与用户内存层。

## 建议的实现顺序

1. 确定简洁 ABI，写用户调用封装和内核分发。
2. 用无需用户指针的调用验证往返流程和返回值。
3. 实现安全复制，再接入用户字符串输出。
4. 完善用户页的申请、权限和回收，接入内存请求。
5. 加入跨页与失败检查，并保持 Lab 4 的隔离证据。

“返回错误”应当是可预测结果；未知调用和错误地址不应让整个内核 panic。

## 实现后怎样观察和验收

| 观察项目 | 应该看到的结果 |
|---|---|
| 调用往返 | 用户发出的调用编号、参数和返回结果符合 ABI |
| 用户输出 | 用户程序通过系统调用输出；没有直接访问 UART |
| 未知编号 | 返回明确错误，用户程序能够继续执行 |
| 跨页字符串 | 合法跨页输入正常；尾页未映射时安全失败 |
| 错误地址 | 内核地址、非规范地址、溢出范围和权限不符均被拒绝 |
| 内存调整 | 成功后可访问新页；失败后旧映射与页计数不变 |
| 回归检查 | 用户陷入、隔离、时钟与串口仍正常 |

可以加入可开关的调用追踪，显示进程编号、调用名和结果；读取字符串前仍必须完成地址检查。正常运行默认保持简洁，避免追踪输出掩盖程序行为。
