## 这一阶段要达到什么

现在的 `pgos>` 在内核的 S 模式运行。用户进程应当拥有自己的程序、栈、寄存器状态和受限制的内存访问权限，并真正进入 U 模式执行。

先实现一个进程即可：加载很小的用户程序，让它执行简单计算，再通过专门的测试异常回到内核。计算结果和异常记录应证明用户代码确实运行过，而不是内核打印一行“用户进程启动了”。

用户代码不能直接调用内核的 `console_printf()`，也不能直接写 UART 寄存器。正常的系统调用入口和用户打印留给 Lab 5。

## 建议的模块布局

以下是候选职责，不是已经存在的源码，也不冻结函数名。

| 候选文件 | 负责什么 |
|---|---|
| `kernel/main.c` | 在原有基础初始化完成后调用进程启动流程 |
| `proc/process.c` | 创建第一个进程，记录编号、用户入口、页表和内核栈 |
| `include/process.h` | 声明最小进程信息和进程操作接口 |
| `mm/user_vm.c` | 为用户代码、数据和栈建立最小隔离映射 |
| `trap/user_entry.S` | 用户陷入时切换到内核栈，保存寄存器；返回时执行 `sret` |
| `trap/user_trap.c` | 区分用户异常、用户期间的中断和内核自身异常 |
| `user/start.S` | 用户程序入口，准备进入用户 C 函数 |
| `user/first.c` | 不依赖系统调用的小程序，用于证明 U 模式执行 |
| `user/linker.ld` | 决定用户程序自身的代码和数据布局 |
| `tests/user_process.c` | 检查用户执行、栈隔离和访问权限 |

沿用已有 `boot/`、`kernel/`、`mm/`、`trap/`、`drivers/`、`lib/`、`monitor/`、`tests/`、`include/`。新目录 `proc/` 和 `user/` 分别承载内核中的进程机制与用户程序。

## 哪些前阶段接口需要扩展

物理页仍由 `page_alloc()` 分配，进程销毁时需要成对归还。用户代码、用户栈、内核栈和页表页的归属必须明确，创建失败也要清理已经取得的页。

当前 VM 操作围绕内核页表。需要补充“针对指定用户地址空间创建、查询、映射和销毁”的能力。用户页要设置 U 权限；内核内存和设备不能顺手标成用户可访问。

当前异常入口处理 S 模式中的异常。用户入口需要从安全的内核栈开始保存现场，不能直接信任用户 `sp`。返回时明确设置用户 `sepc`、用户栈及 SPP 状态。

Lab 3 的时钟和串口中断在用户执行期间仍应正常处理。原来的内核诊断台可以留作测试入口，但它不是新用户进程。

## 建议的实现顺序

1. 保留 Lab 3 检查，建立进程记录和独立的内核栈。
2. 准备小用户程序，给代码、数据与用户栈分配物理页并建立权限。
3. 实现 U → S 的入口保存，再实现 S → U 的返回路径。
4. 进入用户程序，通过可识别的计算和测试异常记录证明它运行。
5. 检查错误路径与资源回收，再检查用户运行期间的设备中断。

这一步只要求建立最小进程执行基础，不提前实现完整调度、文件系统或 Shell。

## 实现后怎样观察和验收

| 观察项目 | 应该看到的结果 |
|---|---|
| 用户执行证据 | 用户入口 PC 正确；陷入记录表明先前模式为 U；计算结果符合预期 |
| 两种栈 | 用户栈和内核栈地址不同；陷入后在内核栈处理 |
| 隔离检查 | 用户访问内核地址、UART 或受保护代码时被拒绝 |
| 中断兼容 | 用户计算期间仍有时钟计数，串口处理正常 |
| 创建失败 | 页不足或加载失败时没有部分进程遗留，也没有页计数泄漏 |
| 回归检查 | 原有启动、物理页、页表和中断检查继续通过 |

可以增加“进程启动卡片”：展示 PID、用户入口、用户栈、内核栈与页表根。这是对真实状态的可视化，不作为用户程序已经运行的替代证据。
