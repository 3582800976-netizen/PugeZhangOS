# Lab 3：让内核响应时钟和输入

这一目录是 **Lab 3 的完整独立版本**。启动、打印、物理页和页表代码也在这里，因此可以直接编译、运行；不需要去另一个实验目录寻找文件，也没有按 `LAB` 宏隐藏不同阶段代码。

Lab 3 要解决的问题是：内核正在执行时，如果时钟到了，或者用户按了键，怎样暂时停下当前工作、处理这个事件，然后准确回到原来的位置？

## 运行并观察

在仓库根目录执行：

```bash
make -C lab3 qemu CPUS=3
```

也可以进入本目录后执行 `make qemu CPUS=3`。`CPUS` 是模拟的 CPU 核心数，可选 1～8。构建产物在本目录的 `build/cpu3/` 等目录中，不会覆盖 Lab 1 或 Lab 2 的产物。

看到 `pgos>` 后，依次输入：

```text
boot
ticks
ticks
irq
echo hello-lab3
irq
test
quit
```

两次 `ticks` 的数值应该增长；输入字符后，`irq` 显示的串口中断数和接收字节数应该增长。`test` 运行实际自检；`quit` 关闭 QEMU。诊断台属于内核，在 S 模式执行。

## 建议按这条线阅读

先看 `kernel/main.c` 的 `kernel_main()`。它只负责启动编排，具体逻辑在各子系统中。找到 `trap_init_hart()`、`uart_enable_rx_irq()` 和 `trap_enable()`，确认中断在什么时候打开。然后依次看：

1. `trap/trap.c` 的 `trap_init_hart()`：设置 CPU 进入中断时跳转的位置。
2. `trap/entry.S` 的 `kernel_vector`：保存当前执行的寄存器。
3. `trap/trap.c` 的 `trap_handle()`：判断事件类型并选择处理方式。
4. `drivers/plic.c`：设备中断如何领取和完成。
5. `drivers/uart.c` 的 `uart_intr()`、`uart_getc()`：输入从设备走到缓冲，再走到主程序。
6. `lib/sbi.c` 的 `sbi_set_timer()`：如何预约下一次时钟事件。
7. `monitor/monitor.c` → `monitor/diagnostics.c`：输入怎样变成命令，怎样读取各子系统的状态。
8. `tests/selftest.c`：怎样验证启动时的多核竞争，以及怎样重复模块自检。

这些文件都在本目录；中断主路径不需要在不同实验之间跳转。

子系统边界也为后续实验保留了明确位置：物理页和页表归 `mm/`，处理进入内核的事件归 `trap/`，硬件访问归 `drivers/`。后续进程、系统调用和文件系统可以通过这些已有接口接入；具体扩展方案见上层架构说明，不提前加入未实现的空源码。

## CPU 被打断以后发生什么

```text
原来的程序执行到某个位置
  → 时钟或设备发来通知
  → CPU 记录返回位置和原因，跳到 stvec 指定的地址
  → kernel_vector 把通用寄存器保存到当前核心的栈
  → trap_handle 判断并处理事件
  → 汇编恢复寄存器和返回位置
  → sret 回到原来的执行过程
```

几个寄存器可以这样记：

| 寄存器 | 保存什么 |
| --- | --- |
| `stvec` | 发生中断或异常时，先执行哪段代码 |
| `scause` | 为什么进入处理流程：时钟、设备，还是程序访问出错 |
| `sepc` | 返回时应继续执行的位置 |
| `stval` | 异常相关信息，例如访问失败的地址 |
| `sstatus`、`sie` | 当前核心是否允许中断，以及允许哪些种类 |

硬件不会自动替我们保存全部普通寄存器。C 处理函数会使用这些寄存器，因此入口汇编先保存，返回前再恢复。这里的栈帧为 272 字节，保持 C 调用需要的对齐。

处理普通中断时，`sepc` 已经是正确的继续位置，不能随意加 4。代码中只有特意发出的、明确为四字节的 `ebreak` 自检指令，才使用 `pc + 4`。页权限自检则跳转到预先指定的恢复位置。

## UART 输入如何走到诊断台

```text
你在终端输入字符
  → QEMU 的 UART 收到字符
  → PLIC 把 UART 的通知交给某个核心
  → CPU 进入 S 模式外部中断
  → plic_claim() 领取中断号 10
  → uart_intr() 读取字符，存进 256 字节环形缓冲
  → plic_complete() 告诉控制器本次处理已完成
  → 主执行流调用 uart_getc()，取出字符并编辑命令
```

PLIC 可以理解为多个设备通知 CPU 的转接站。设置优先级、允许 UART 这一路通知，并设置当前核心能接收的通知范围，三部分都要完成。

环形缓冲是一个会循环使用的数组：一个位置记“接下来写哪里”，另一个位置记“接下来读哪里”。中断处理函数负责写，启动主核的诊断台负责读。发布位置时使用原子操作，保证读取者先看到已经写好的字符。

中断处理函数只接收字符和更新计数，命令解析在主执行流完成。这样可以缩短中断处理时间。输出仍然采用等待串口可发送后再写入的方式。

## 时钟如何持续发生

```text
通过 SBI 预约一个未来的时间点
  → 到达时间点，固件使 S 模式收到时钟中断
  → 本核心 ticks 加一
  → 重新预约下一次
  → 返回原来的执行位置
```

每个核心单独设置定时器并记录计数。当前 QEMU 时间基准为 10 MHz，每次预约间隔为 100000 个时间单位，对应目标频率 100 Hz。处理时间和模拟运行速度会影响实际观测，因此 `ticks` 表示中断次数。

诊断台在没有输入时执行 `wfi` 等待事件。定时器也会定期唤醒核心，让它重新检查输入缓冲。

## 为什么先准备好再开中断

启动主核先准备打印、PLIC、物理页和共享页表，再启动其他核心。每个核心启用自己的页表、安装陷阱入口、设置 PLIC 和定时器，随后发布“准备完成”。其他核心发布状态后即可打开各自的 CPU 中断开关。主核等待所有核心完成后，再打开 UART 输入中断和主核自己的 CPU 中断开关。

如果先开中断，事件可能在入口地址、接收缓冲或页表还未准备好时发生。顺序本身就是架构的一部分。

锁还会暂时关闭当前核心的中断，并在最外层锁释放后恢复原来的状态。这样可避免同一核心在持有某把锁时，被中断处理函数打断后再次等待自己持有的锁。

## 能展示的小巧思与验证依据

- `boot`：显示各核心实际经过的启动阶段、独立栈范围和 `satp`。
- `vm 40000000`：查看诊断别名映射；自检通过两个地址实际读写同一物理页。
- `mem`：显示页池状态，错误归还会被拒绝，自检结束后空闲页数恢复。
- `ticks`、`irq`：计数来自真实中断路径，方便演示事件确实持续发生。
- `test`：检查格式化边界、页分配、MMU 权限和陷阱寄存器恢复。

仓库根目录的 `scripts/check.py` 负责自动运行检查；本目录负责独立内核实现。自动检查会实际发送串口字节、比较多次时钟计数，并要求模拟机器正常退出。重构后的运行证据以仓库中的最新检查日志为准。

本实验针对 QEMU `virt`、128 MiB RAM。OpenSBI 提供 M 模式底层服务，内核从 `0x80200000` 进入 S 模式。`quit` 使用该 QEMU 的 32 位关机设备写入，避免旧版固件关机访问宽度不兼容的问题。
